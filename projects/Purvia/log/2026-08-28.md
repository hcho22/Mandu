## The headline: the receipts-rot crisis is over (resolved 2026-08-21 → 08-28)

For three syncs this tracker described the same slow-motion failure - the nightly eval series stopped publishing to `main`, receipts stranded on `eval-publish/*` branches, "kill criterion 4 in motion," preconditions 1 and 2 red.
The root cause was always the same: the auto-merge publish path (#109) authenticated with `EVAL_PUBLISH_TOKEN`, an expiring/empty PAT, so every scheduled run pushed its snapshot branch but died at `gh pr create`.

**#121** (`999ae74`, 2026-08-21) fixes that at the root: the eval-publish PR token is now **minted at run time from a GitHub App** (`EVAL_PUBLISH_APP_ID` / `EVAL_PUBLISH_APP_PRIVATE_KEY`) instead of a human-held PAT that silently expires.
The publish commits now carry the `app/purvia-eval-publish[bot]` author, which is the visible signature that this is live.
This is the single most load-bearing change in the whole update - it retires the failure mode that had recurred four times (the 18-night June outage, the seven-week dead lexical leg, the 07-16 stop, the 08-12 empty-token stall).

**#128-#131** (`0193bcc` / `b359ea5` / `3a48a53` / `1cbee7b`, all merged 2026-08-24) landed the stranded receipts: the 2026-08-20 and 2026-08-21 permissions-scale and retrieval nightlies were backfilled onto `main` verbatim from their CI-authored snapshots, no eval re-run and no number edited.
Captain-authorized cleanup of the stranded `eval-publish/*` branches accompanied them.

**#132-#136** (2026-08-27), **#138-#140** (2026-08-28), and the weekly **#135/#136** are the proof the series now publishes on its own: the retrieval, reranker-observability, permissions-scale, E7-escalation, and RAGAS snapshots are landing on `main` under the bot author with no owner intervention.

## Luna answerer - open reconciliation item (flagging, not asserting)

The 2026-08-21 tracker and the current README both say "the retrieval eval answerer moved to `gpt-5.6-luna` (#115, US-120)."
That is **half true**, and the two halves point in opposite directions, so I am recording it as an open reconciliation item rather than restating either claim cleanly:

- **The eval answer generator did move to Luna and is still there.** Verified: `evals/retrieval/runner.py:217` reads `GENERATION_MODEL = "gpt-5.6-luna"`; #115 (`9737e1d`, merged 2026-08-20) landed it and nothing has reverted it.
- **The production/runtime answerer migration was HALTED.** The runtime answerer default is unchanged at `gpt-4o-mini` (`backend/escalation.py:1098`, `DEFAULT_ANSWERER_MODEL`), and the migration PRD (`.claude/agent/tasks/prd-luna-answerer-migration_2026-08-20.md`) states the answerer migration is **HELD pending "purvia-answerer-model-reconsider"**, with the copy-pasteable Luna deployment env block (US-122) deliberately not delivered.
- **The reason for the hold, per firstmate's records, is cost:** a 2026-08-21 measurement found Luna ~1.85x dearer than `gpt-4o-mini` on the answerer path (Luna bills reasoning tokens as output) and slower. I could **not** find a committed cost writeup in the repo - US-124's acceptance boxes in the PRD are all still unchecked, and no `*cost*` / `*reconsider*` doc exists - so the 1.85x figure is a firstmate-records claim I cannot corroborate from the checkout.
- **The live contradiction this creates:** the migration PRD's own FR-1 requires the eval's `GENERATION_MODEL` to *equal the production answerer model* ("they must move in lockstep"). With the production migration held at `gpt-4o-mini` but the eval generator left on Luna, the eval no longer mirrors production. Either the eval generator should be reverted to `gpt-4o-mini` or the production migration should resume - that is an owner call, not something to paper over. The README's Luna claim should be narrowed to "the *eval* generator moved to Luna; the *production* answerer migration is held at `gpt-4o-mini`."
