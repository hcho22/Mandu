# Own the Problem, Not the Code

The principle that as code gets cheap, durable value moves to deep problem-understanding and domain ownership, not the code itself.

## Two sources

- [[ai-era-50-career-tips]]: when code becomes cheap, high-quality ideas become more valuable; go deep into one domain and own that problem space to root level (via Steve Jobs: knowing which ideas *not* to pursue matters as much as which to build).
- [[inside-conductor-workflow]]: the architecture-scale version - humans own the core concepts and contracts ([[dont-let-ai-be-your-architect]]).

## Key points

- Deep domain knowledge and problem-framing stay scarce even when implementation is automated.
- Owning the problem includes owning the definition of done and the quality bar, not just the requirements.

## Synthesis

This is the career-and-strategy root of the wiki's recurring stance: hand the code to agents, keep the judgment.
It underwrites [[taste-as-moat]], [[dont-let-ai-be-your-architect]], and [[cost-of-being-wrong]] (choose problems worth owning), and it is the clearest one-line case for hcho's positioning - a validation engineer owns "is this correct and does it matter," which is exactly the part that does not get automated.
